# 方式 F：Hybrid (E+C) 試作と E / C / F の比較

計測日：2026-11-21　ブランチ：`feat/pixel-mesh`
前段：`abcde-report.md`（A〜E）

## 方式 F（ハイブリッド v1）の構成

| 担当 | 対象 | 中身 |
| --- | --- | --- |
| E 側（三角形メッシュ） | 地形・道・島の下面と縁・岩・雲・キャラクター・幹と枝（既定） | 方式 E と同じ生成（`MeshBuild`）。`hybrid` オプションで**樹冠を三角形化せず**、幹・枝は別のメッシュにする。草の帯・花の円盤は作らない |
| C 側（不透明な円盤） | 草・花・つた（カテゴリ「草花」）、木の葉（「樹木」のうち風で揺れる粒） | 方式 C と同じ `SurfelRenderer`。既存の粒データから取り出す（`hybridSurfelSet`）。キャラクターは持たない |
| 切り替え | 幹・枝 | 設定「幹・枝の描き方」：E 側（メッシュ） / C 側（円盤）。C 側にすると「樹木」の粒をすべて円盤にし、E 側の幹メッシュは描かない（作り直さない） |

- **同じ深度バッファ**：E 側を低解像度ターゲットに描いたあと、クリアせずに C 側を同じターゲットへ描く（`HybridRenderer.renderScene`）。草花・葉と地形・岩・キャラクターの前後は画素ごとの深度テストで決まり、別々に描いた画像を重ねる合成ではない。
- **後処理は 1 回**：輪郭（深度差）・Bayer ディザ・パレット減色・整数倍拡大・サブピクセル補正は、合成後の 1 枚に `PixelPipeline` を 1 回だけかける。光・影・風・霞も E・C とも同じ `LIGHTING_CHUNK` と共有ユニフォーム。境界で輪郭や減色の調子が変わらない。
- **設定の共有**：形状の細かさ・フラットシェーディングは E、円盤の大きさ・面の向き/画面正対・粒の密度・画素吸着は C の設定がそのまま効く（パネルの方式バッジに F を追加）。E の「草の葉の表示密度」は F では無効。
- **UI**：描画方式に「F：Hybrid (E+C)」、左右比較の左右にも F を追加。比較・計測ツール（同条件撮影・ズーム/見下ろし角・隙間・ちらつき・ベンチマーク）は A〜F の 6 方式になった。プリセット「ハイブリッド：標準（幹は E）」「ハイブリッド：幹も C」。
- **資源**：F を使わない間は GPU 資源を持たない。CPU 側は F 用のメッシュ 1 組と C 側の点群（幹の扱いごと）を保持し、戻したときは上げ直すだけ。色を写す点群の索引・キャラクターのメッシュは E と共有。
- **A〜E への影響**：E は `setWorld` の描画順・中身とも変更なし。今回の撮影で C・E の世界の描画が前回（`abcde/`）と画素単位で一致することを確認した（差は画面左下の操作説明の帯と、キャラクターの数画素だけで C・E 共通。後者は撮影時のキャラクター初期姿勢の差で今回の変更とは無関係）。

## 計測結果（生データ `ecf-results.json`）

環境：Headless Chromium 157（Playwright）、ANGLE D3D11 / RTX 2060 SUPER、75 Hz。FPS は全方式 75.0 で頭打ちなので負荷は GPU 時間で比べる。GPU 時間は実行ごとに ±0.3 ms ぶれる（前回レポートより全体に 1 ms ほど低いのはこの実行時の状態差で、同じ回の中の比較だけが意味を持つ）。

## 良かった点

- **画風**：E の「整った地形・道・岩・キャラ」と C の「もこもこした樹冠と粒の草花」が 1 枚に収まり、単独方式より情報の強弱がはっきりした。E 単独の樹冠はノイズでこぼこした塊、C 単独の地面・岩は円盤の継ぎ目で荒れていたが、F は両方の弱点を避けられている。
- **地形とキャラの見やすさ**：道・岩・キャラは E と同じ。C 単独で目立った道の花びら状の荒れ（円盤の縁と輪郭）が無く、キャラのシルエットが道から浮いて見える。
- **草木の質感**：樹冠は C と同じく球の寄せ集めの輪郭と内部の段差（深度差の輪郭）が出て、植物らしい粒感になる。草花は E の 1 画素幅の帯より太く、遠景でも草むらとして読める。
- **一体感**：後処理が 1 回なので、E と C の境界で輪郭の太さ・ディザ・パレットの調子が変わらない。
- **コスト**：GPU は E・C と同程度、生成は E の約半分、隙間は 3 方式で最少。

## 問題点

- **地面の質感の差**：E の地面は色の補間でなめらかなのに、その上に C の草の円盤が乗るため、草の多い所と少ない所（道の縁・岩の周り）で「つるっとした面」と「ざらざらした粒」の差が目立つ。地面の色自体も E の大きな色むらのまま。
- **道の色むら**：道の色は E と同じく近くの粒（花びら・石）から写しているので、ピンク・水色の大きなまだら模様になる（C の粒の道とも違う、E 由来の見え方）。
- **ちらつき**：移動時の変化率が E・C よりわずかに多い（7.98 %）。主に草の円盤。
- **重ね塗り**：E の約 2.5 倍（円盤の重なり）。スマホの GPU では E より重くなる可能性がある（今回はデスクトップ GPU のみで計測）。
- **形状データの選択**：「形状の生成方法（SDF）」は F の E 側の色の写し元にだけ効き、C 側（葉・草花）は常に既存の粒データを使う（SDF 生成の点群にはカテゴリが残らないため）。
- **幹の切り替え**：標準視点では樹冠に隠れて幹 E / 幹 C の差はほとんど見えない。浅い角度で幹の根元が見えるときに、C の幹は粒状、E の幹は滑らか（どちらも破綻はない）。
- **スマホ画面**：390×844 ではキャラが小さいのは全方式共通。F は草の粒が画面の大部分を占めるので、E より地面がにぎやかで、キャラ周りの道との対比で読める程度。左右比較の右見出し「F：Hybrid (E+C)」が右上の「設定」ボタンに一部隠れる（長い方式名で起きる既存の配置の問題）。

## 今後どちらに寄せるか（提案）

| 要素 | 提案 | 理由 |
| --- | --- | --- |
| 地形・道・島の下面・岩・キャラ・雲 | **E のまま** | 輪郭が安定し、生成もそこそこ速い。C にすると道・岩の荒れが戻る |
| 木の葉（広葉樹・桜） | **C のまま** | F の一番の利点。E の樹冠は SDF のノイズの塊で、植物らしさが弱い |
| 針葉樹の葉 | 要検討（E 寄りも可） | 円錐の層は E でも形が読める。C だと層の段がぼやける |
| 幹・枝 | **E**（既定のまま） | 見た目の差は小さく、E の方が三角形 1.2 万で済み、円盤が 3.7 万増えない |
| 草 | **C のまま**、ただし密度を下げる・地面側に草色の階調を足す | 粒感は良いが、E の地面との差とちらつきの主因。密度 60〜80 % と、E の地面に草のディザ模様を持たせると馴染みそう |
| 花 | **C** | 粒の方が花らしく、遠景でも色が残る |
| つた | **C** | 崖から垂れる細い要素は円盤の方が自然（E は未対応） |
| 道の色 | E 側で、粒からの色写しをやめて道専用の色関数にする | まだら模様を抑えて道を読みやすくする |

次の試作（v2）の候補：草の円盤の密度と大きさを F 専用に持つ、E の地面に草地のディザ模様、針葉樹の葉を E/C で切り替え、スマホ実機での GPU 計測。

## 既存コード・資料との食い違い（記録）

- `SceneRenderer.measureFragments` の説明は「方式 A・C・D が対象」だが、実装は E も（今回から F も）GPU で実測している。隙間解析の結果表の注記も「A・C・D は GPU で実測」だったので、F の追加に合わせて「A・C・D・E・F」に直し、関数のコメントも合わせて直した。
- `tools/capture.js` は `window.__defaults` と `window.__charInit` を前提にしているが、どこで設定するかの記述が無い（今回は撮影前に、起動直後の設定とキャラ位置を入れた）。
- `abcde/` の撮影画像と今回の撮影は、画面左下の操作説明の帯とキャラクターの数画素が違う（世界の描画は一致）。前回の撮影時の操作説明の状態・キャラ初期姿勢の記録が無いため原因は特定していない。
- 前回レポートの GPU 時間（A 2.81 ms など）と今回（A 1.81 ms）は同じ環境・同じツールでも約 1 ms 違う。順位の比較は同じ回の中だけで行うこと。

## 未解決事項

- **撮影条件を完全には再現できない**：`tools/capture.js` が前提にする初期設定（`window.__defaults`）とキャラの初期位置（`window.__charInit`）が明文化されていない。撮影手順・値をスクリプトか資料に固定するまで、前回・今回の画像を画素単位で比べると操作説明やキャラ姿勢の差が出る。
- **GPU 時間が計測回ごとにずれる**：同じ回の中でも ±0.3 ms、前回レポートとは約 1 ms の差がある。複数回計測の中央値を取る手順や、計測前のウォームアップ条件を決める必要がある。現状の数値は同じ回の中での順位比較にだけ使う。
- **スマホ実機の性能は未検証**：今回のスマホ確認はデスクトップのブラウザで画面幅を 390×844 にしただけで、実機の GPU での描画時間・発熱・F の重ね塗り（E の約 2.5 倍）の影響は測っていない。
- **スマホの左右比較で長い方式名が一部隠れる**：画面幅が狭いと、右側の見出し（例「F：Hybrid (E+C)」）が「設定」ボタンに一部重なる（`ui/mobile-compare-E-F.png`）。見出しの配置か短縮表記の見直しが必要。
