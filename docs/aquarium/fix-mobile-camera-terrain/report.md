## 1. スマホ入力（仮想スティックが固まる・カメラ操作が戻らない）

### 再現条件と原因

| 症状 | 再現 | 原因 |
| --- | --- | --- |
| スティックが反応しなくなり、カニが歩き続ける | スティックの指の `pointerup` / `pointercancel` がページに届かない（iOS の WebKit は複数の指・システムのジェスチャー・画面端で取りこぼす）。捕捉（`setPointerCapture`）が外れた状態で、スティックの外で指を離す | `TouchControls` は押した要素の `pointerup` だけで終わりを判定し、`id !== -1` の間は新しい指を受け付けなかった。終わりが一度失われると、`touchMove` が最後の値のまま残り、押し直しても無視される |
| 1 本指のドラッグで視点が回らず、ズームになる | 画面ドラッグの指の終わりが失われた後に、もう 1 本で触る | `Input.touches` に古い指が残り、次の指で「2 本指 = ピンチ」になる（測定：1 本指で 100px ドラッグ → 回転 0、ズーム −0.40）。3 本残ると何も効かない |
| 掘る・ジャンプが押されたまま | ボタンの捕捉が外れ、ボタンの外で指を離す／押したままページが隠れる | ボタンも要素の `pointerup` だけで判定。`blur` はキーだけ消し、`visibilitychange` / `pagehide` は扱っていなかった |
| マウスで視点が回り続ける | ドラッグ中にウィンドウの外でボタンを離す | `buttons = 0` の移動を見ていなかった |
| **起動直後・裏から戻った直後に視点が飛んで戻らない** | 読み込み（スマホでは数秒〜十数秒）の直後の最初のフレーム | `requestAnimationFrame` の時刻は「フレームの始まり」なので、重い初期化の直後は直前の `performance.now()` より過去になる（測定：−3.6 秒）。負の `dt` で注視点の追従 `1 − exp(−8·dt)` が発散し、注視点が 10⁹ 単位へ飛ぶ。`dt < −11 秒` なら無限大 → NaN で二度と戻らない（スマホの読み込み時間では起こり得る） |

### 修正した入力管理方式（`src/game/Input.ts`、`src/ui/TouchControls.ts`）

- **持ち主方式**：押されたポインターに持ち主（スティック・ボタン・視点のドラッグ）を `Input.claim` で付け、
  動き・離した・取り消しは `window` の捕捉段階で受ける。要素の捕捉が外れても、別の要素の上で離しても届く。
  終わったら持ち主の `end` を 1 回だけ呼ぶので、スティック・ボタン・ピンチは必ず元に戻る。
- **タッチの一覧と照合**：`touchstart / touchend / touchcancel` の `TouchEvent.touches`（WebKit でも正しい一覧）と、
  押しているタッチのポインターを 80ms 後に照らし合わせ、一覧に無い指（位置で対応を取る）を終わらせる。指が全部離れたら全部終わる。
- **同じ番号の押し直し・順序の入れ替わり**：終わっていない番号で押されたら、古い持ち主を終わらせてから付け替える。
  スティックは、前の指が残っていても新しい指に付け替える（固まっても押し直せば直る）。
- **ページが隠れる**：`blur` / `visibilitychange(hidden)` / `pagehide` で、押している物・キー・スティック・ボタン・ピンチをすべて戻す。
- **マウス**：ボタンが離れた状態（`buttons = 0`）の移動、`lostpointercapture` で終わらせる。
- **時間差**：`main.ts` のループで `dt` を 0〜0.25 秒に制限（負の時間差を 0 に）。カメラ側でも `dt` を制限し、
  値が NaN・無限大になったら既定の視点へ戻す（`AquaCamera.sanitize`）。
- **CSS**：水槽ページだけ `touch-action: none`（html / body）・`overscroll-behavior: none`・長押しメニューと文字選択を止める
  （HUD・説明の上から始めた指でページが拡大・選択されない）。

## 2. 冒険カメラ

### 現状の方式の問題（原因の分析）

| 症状 | 原因（修正前の `AquaCamera.orbitPose`） | 測定（修正前） |
| --- | --- | --- |
| カメラが勝手に別方向へ回り込む | 狭い所で `swing`（±0.4〜1.6 rad の横回り込み）を足し、移動の向き（`camera.yaw`）にも足していた | 流木・洞窟・トンネルで 1 周回すと最大 1.08〜1.27 rad 回り込む。トンネルで「横から」を指定しても後ろへ戻る |
| 地面・天井で視点操作が過剰に制限される | 掘ったトンネルの中では仰角を水平近く（−0.08〜0.09）へ強制。大きく寄らされると勝手に持ち上げる（`raise`） | 高い仰角を指定しても水平の絵になる |
| 壁で急に近づく | 遮蔽の判定（`castFree`）が上向きの面（台の天板・かごの上）を素通りし、カメラがその中に入ってから安全網で一気に注視点側へ戻す | 濾過槽で 1 フレームに 0.41、水槽台で 0.36 の急な寄り |
| 見たい景色が入らない | 薄い物（流木の殻・枝・台の板）でも必ず手前で止まる | 流木トンネルで 3.2 → 0.9、流木の小屋で 0.65 |
| 異常から戻らない | 上の負の時間差・NaN | 起動直後に注視点が 10⁹ へ飛ぶ |

### 採用した方式と選定理由

比較した 3 案：

1. **位置補正（バネの腕）だけ**：カメラを固体の手前で止める。地形の裏側は絶対に見えないが、薄い殻の中や狭い所では寄り過ぎる。
2. **局所的な透過（ディザで抜く）**：カメラを遠くに置き、カメラとカニの間の物を抜く。景色が保てるが、厚い物を抜くと
   中身の無い断面（裏側・その向こう）が見える。
3. **断面表示**：抜いた所に断面（蓋）を描く。砂（高さ場 + 掘った空洞）は閉じた形ではなく（底が無い）、空洞は CPU 側の
   SDF にしか無いので、方式 F v2 の描画（三角形 + 円盤、低解像度 + 後処理）の中で正しい断面を作るのは重い・壊れやすい。

**採用：1 と 2 の組み合わせ（物の厚さと種類で使い分ける）**

- 視点の向き（yaw / pitch）はプレイヤーのまま変えない（回り込み・持ち上げ・トンネルの水平化を削除）。
- 床は従来どおり「床の上に留めて、その分を見上げる」。**天井も同じ考え方**で「天井の下に留めて、その分を見下ろす」
  （操作が止まったように感じない）。
- **薄い物**（流木の殻・枝・岩の縁・台の板・家具。腕に沿った厚さ 1.5 以下で、その先にカメラを置ける）は距離を縮めずに越え、
  カメラとカニの間の区間だけを **ディザで抜く**（`OCCLUDER_CUT`。カメラを頂点とする円すい = 画面上のカニのまわりの円、
  カメラからの距離で越えた区間だけ）。方式 F v2 のディザ・ピクセル表現と馴染み、薄い殻なので抜いても内側の面が見えるだけ。
  付いている苔（C 側の円盤）も同じ範囲で抜く。
- **砂（底床・掘ったトンネル）と厚い岩は越えない**：抜くと中身の無い断面が見えるので、手前でなめらかに止める
  （寄るのは速さ 9、離れるのは 2.5 の指数。左右 0.8 幅を先読み）。寄らされて近いときは画角を最大 +16° 広げる。
- 越えた薄い物の中をカメラが通る間は安全網で引き戻さない（引き戻すと、外へ出る向きに越えられず手前で止まり続けた）。
- 値が NaN・無限大になったら既定の視点へ戻す。

## 3. 掘削中に壁が消える問題

### 原因（2 つ）

1. **見た目と当たり判定のずれ（主因）**：かき出すと当たり判定（SDF）は即座に変わるが、区画のメッシュは 1 フレームに
   時間の上限（6ms、最低 1 区画）ずつ作り直していた。待ちの区画（スマホ相当で最大 27 区画）では、
   - カニ・カメラが新しい空洞へ入るが、見た目ではまだ固体の中 → 固体の外向きの面は裏面（`FrontSide` で描かれない）なので、
     **向こう側（水・ガラス・水槽の外）が透けて見える**。
   - 作り直した区画と待っている区画の境で、空洞の壁が片側だけになる。
   4 倍遅い CPU で掘りながら視点を回すと、`sheet-dig-x4.jpg` 上段のようにトンネルの奥の壁が抜けて水が見える。
2. **Surface Nets の折れ返った三角形（副因）**：ねじれた四角形を決まった対角線（a–c）で分けると、片方の三角形が
   裏返って空洞の外（砂の中）を向く。`tri()` の向きの補正は格子の軸の向きで行うため、このとき 1 枚だけ逆を向き、
   **トンネルの内側から見ると小さな穴** になる（区画の継ぎ目に沿って出やすい）。

検証で問題なかった項目：隣の区画との継ぎ目の重なり（半マス重なっていて隙間は無い）、メッシュの重複による深度競合
（重なる部分は同じ格子の同じ頂点なので同じ深さ・同じ色）、カメラのめり込み（ニア 0.05 に対して面から 0.1 以上離す）。
4×4×4 のブロック省略も、値が下限（PAD）で頭打ちになるだけで符号は保たれていた（ただし省略がほとんど効いていなかった → 下の性能）。

### 修正

- **2 つの版（`AquariumDig.ts`）**：かき出しは「最新の形」だけを書き換える。描画側は作り直しを始めるときに形を写し
  （`snapshot` = `snap` の版）、その版で区画を作る。全区画ができたフレームで **一斉に差し替え、同じ瞬間に当たり判定へ入れる**
  （`commit` = `live` の版）。当たり判定（カニ・カメラ・照準）は `live` しか見ないので、見た目に無い空洞へ入らない。
- **ひとまとまりずつ差し替え（`AquariumDigFx.ts`）**：区画をばらばらに差し替えない（境で壁が片側だけにならない）。
- **折れない対角線（`MeshBuild.surfaceNets` の `foldSafe`）**：2 通りの分け方のうち三角形の向きが揃う方を選ぶ。
  掘った区画だけで使い、既存の岩・流木・比較ページのメッシュは変えない。
- **作り直しを軽く（`DigField.meshValue`）**：空洞から遠い深い砂では砂の距離をそのまま返し、ブロック省略を効かせる
  （同じメッシュ。1 区画 10.0 → 9.0 ms）。

### 結果

| 検査 | 修正前 | 修正後 |
| --- | ---: | ---: |
| 掘りながら視点を回す（CPU ×4、10 秒、`dig_test.js`）：画面 15 方向の光線が最初に **裏面** に当たった数 | 67 | **0** |
| 掘り終えたトンネルの壁の穴（`mesh_check.js`：トンネルの中の 164 点 × 100 方向、SDF の壁とメッシュを比較） | 22（裏向き 19・欠け 3） | **0** |

`dig_test.js` の「何にも当たらない光線」（修正後 67 本）は、トンネルの入口（水に開いた口）の方を向いたもので、壁の抜けではない
（画面でも確認）。格子（0.1）より薄い膜（地表すれすれの薄皮）はどちらのビルドでも三角形にならないので数えていない。

## 6. 残っている問題

1. **iPhone 実機で確認していない**。取りこぼしは「通知を握りつぶす」模擬と CDP のタッチで再現・確認した。
   タッチの一覧との照合は位置で指を対応させるので、2 本の指がほぼ同じ所にあると、失われた方ではない指を終わらせることがありうる
   （その指は押し直せば戻る）。
2. **掘ったトンネルの中で横・前・上を向けると、カメラが壁の近くまで寄る**（0.5〜0.9）。向きを勝手に変えない・砂は抜かない
   方針の結果で、画角を広げて補っている。広く見たいときは後ろ向きに回す必要がある。
3. **遅い端末では掘り進みが遅れる**：当たり判定を見た目と同時に変えるので、CPU ×4 の条件では 1 回のまとまりに 0.3〜0.5 秒かかり、
   10 秒で進む距離が 11.5 → 9.7 に減った。進む高さも変わり、水面の高さ（5.5）にかかるトンネルでは水面（内側から見た水面の板）が
   トンネルの天井の位置に見える（物理では水中扱いなので不整合ではないが、見た目が平たい）。区画の作り直し（頂点の色付けが半分近く）を
   さらに軽くする・Web Worker に移すのが次の候補。
4. **厚い岩の向こうからは抜かない**ので、洞窟の横・岩の柱の裏ではカメラが寄る（修正前と同じ距離）。
5. 越えた薄い物の中を通る一瞬（1 周回したうち流木で 26 フレーム）は、カメラが物の中にいる。抜いて描くので視線は遮られないが、
   その物の他の面は内側から見えない（周りが一瞬抜けて見える）。
6. 描画比較ページ（`src/main.ts:138`）のループにも同じ負の時間差の式がある。比較ページは画素を変えない方針なので今回は触っていない。
7. 区画を三角形にするとき、格子（0.1）より薄い膜は三角形にならず、当たり判定だけに残る（地表すれすれを掘ったときの薄皮）。
