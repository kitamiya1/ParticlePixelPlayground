PR #3（壁登り `89df18b` ＋ ガラス越しの巣穴観察 `bf7e17c`）の上の 3 つ目のコミット。比較の「変更前」はすべて `bf7e17c`

## 1. ガラス際の地形メッシュの穴

### 原因

- 掘った区画の断面は、砂の距離関数をガラスの内面の 0.015 内側の面で切って、格子 0.1 の Surface Nets で三角形にしている。
  格子はガラスの面に揃っていて、面の上（e = 0）と 1 列目（e = 0.1）の格子点の値だけで断面の位置が決まる。
- トンネルの突き当たりがガラスの手前 0.1 前後で止まると、空洞とガラスの間に格子より薄い砂の板が残る。
  1 列目の格子点がわずかに空洞（値 +0.01 前後）でも、その少し奥（e = 0.10〜0.12）には砂が残る。
  見た目は断面も突き当たりの壁も作られず外が透けるのに、当たり判定には板がある（直径約 0.05 の抜けが点々と並ぶ）。
  突き当たりは丸いので、板の厚みは場所ごとに格子の 1 マスをまたいで変わる。そのため PR #3 の `glassFilm`
  （膜の厚さ 0.12 未満を開ける）では境目に必ず 1 点の板が残った。
- ガラスまで届いたトンネル（16 秒まっすぐ掘って右のガラスへ届く）でも、床とガラスの角に同じ抜けが一列に並び、
  中から見ると床とガラスの間に明るい線が出ていた（`sheet-pinhole.jpg` の longtunnel-inside）。

### 直し方（`AquariumDig.carveAt`。見た目と当たり判定の両方）

- ガラスの内面から 1 マス（0.1）より近い所の空洞の値を、1 列目の値 c1 から、ガラスへ近づくほど傾き 2 で下げた値にする
  （`c1 − 2 ×（0.1 − e）`、角では両方の面から）。
  - 1 列目が空洞（c1 < 0）なら面まで空洞、砂なら 1 列目まで砂が続く。格子より薄い板が残らない。
  - 面に垂直な向きには値が 1 次式なので、Surface Nets の辺の補間で出る断面の位置と当たり判定の面が一致する。
- 試した傾きと不一致の数（`mesh_check`、約 3.8 万本）：0（そのまま延ばす）59、0.5 で 24、1 で 13、2 で 6。
  - 傾き 0 では、突き当たりが 1 列目ちょうどの所で値が 0 に近い平らな帯になり、砂のかけらが点々と残った。
  - 傾きを上げると、穴の縁とガラスの角に残る砂のくさびも小さくなる。
- 空洞から 0.3 以上離れた砂は下げない（作り直さない区画の砂の値を変えない）。
- 代わりに、ガラスの面での穴の輪郭が最大 0.2 広がる（漏斗のような面取り）。
- PR #3 の `glassFilm` は不要になったので外した。

## 2. ガラス際の掘削の負荷

### 原因（CPU プロファイル：右のガラス際まで掘った区画を 4 回ずつ作り直す、デスクトップ）

| | ガラスに接する区画 | それ以外 |
| --- | --- | --- |
| 区画 1 つ（変更前） | 10.1 ms | 6.2 ms |
| 時間の内訳（変更前） | `clip` 23%・`carve` 22%・`primDist` 16%・`solid` 6% | 同じ傾向 |

- 時間のほとんどは、空洞の距離関数（`carve` → `clip`・`primDist`）。
  - `clip`（掘れない場所：底・ガラス・管の区画・発見物）は、空洞の近くの標本ごとに、すべての管の区画・発見物を
    `Math.hypot` で調べていた。
- ガラスに接する区画が重い理由：断面の近くは格子のブロックを飛ばせない。そのため空洞の高さの範囲で評価が多い。
- 断面の下の部分（空洞より下）は、PR #3 の `deepY` で既に安くなっていた。そこだけを保持・省略する案（下記の `stripCap`）は
  作り直しの時間をほとんど変えなかった（右 7.8 → 7.2 ms）。

### 直したこと

1. `AquariumDig.clip`：管の区画・発見物を、いまの値より大きくなりうる近さのときだけ平方根を取る（2 乗の距離で先に判定）。
2. `AquariumDig.carve`：外接箱までの距離を 2 乗で判定し、いまの値に効かない空洞は平方根なしで飛ばす。
3. `primDist`：カプセルを `Math.hypot` の代わりに平方根で計算する（共有の `sdCapsule` は変えない。描画比較ページ A〜F は同じ）。
4. ガラスに接する区画：ガラスの面の外の格子点は距離関数を調べない（符号だけ要る）。
5. 断面の下の部分（空洞・地表より十分下の平らな断面）は Surface Nets を使わず、同じ格子の頂点・四角形を並べる
   （`stripCap`。角の区画を除く）。継ぎ目の頂点は同じ位置で、光線検査の結果は 1 本も変わらない。

値は丸め誤差の範囲で同じ：脱出の検査 20 / 20 が変更前と同じ結果。`mesh_check` は 4 → 3 本（ガラス際の 1 本が丸めで消えた）。

### 結果

デスクトップ、区画 1 つの作り直し（同じ区画を 4 回ずつ）：ガラスに接する区画 10.1 → **5.1 ms**、それ以外 6.2 → **3.4 ms**。

## 3. 流木（中空の倒木）付近のカメラ

### 原因（1 フレームごとの記録。`climb_config` の「流木（中空の倒木）」）

1. **床で上げた仰角の戻し方**：倒木の上から降りて床が無くなると、仰角の下限（`floorPitch`）が番兵の −2 へ向かって戻る。
   その差が大きいので、離れ始めの 1 フレームに 0.16 rad も仰角が下がり、カメラが振れていた。
2. **薄い物を越えられなくなったときの安全網**：
   - 倒木は、薄い物として「越えて描画で抜いて」いた（腕に沿った長さ 1.0〜1.4）。
   - カニが倒木の向こうへ沈むと、腕に沿った長さが THIN（1.5）を超えて越えられなくなる（`passed` が 1 フレームで空になる）。
   - 倒木の向こうにいたカメラは寄り始めるが、すぐ倒木の裏の面に近づき、めり込みの安全網（`orbitPose` の 4）が
     1 フレームで倒木の手前（カニの近く）へ移していた（0.88。跳んで越えると 1.36）。

### 直したこと（`AquaCamera.orbitPose`。見る向き・プレイヤーの yaw / pitch は変えない）

1. 床・天井が無くなったときは、番兵ではなくいまの仰角までゆっくり（係数 4）戻し、戻りきったら番兵にする。
2. 直前のフレームまで越えて抜いていた物を越えられなくなったとき、カメラがその物の手前の面より向こうにいれば、
   1 フレームで飛ばさない。その物を抜いて描いたまま、毎秒 8（`TRAVERSE_SPEED`）で手前へ抜ける（`traverse`）。
   その間は安全網で押し戻さない（既存の「越えた物の中を通る」扱いと同じ）。

### 結果（1 フレームのカメラの位置の最大の動き）

| 場面 | 変更前 | 変更後 |
| --- | --- | --- |
| 中空の倒木を越えて向こうへ降りる | 0.88 | **0.21** |
| 倒木を跳んで越える | 1.36 | **0.28** |
| 倒木を反対向きに跳んで越える | 0.97 | **0.36** |
| 倒木を引いた視点（zoom 4.5）で越える | 0.70 | 0.52（置いた直後の寄り。越えるときではない） |
| 岩の垂直面 / 岩の壁を横へ | 0.36 / 0.36 | 0.32 / 0.08 |
| ガラス 左 / 右 | 0.57 / 0.44 | 0.16 / 0.05 |
| 流木の小屋・水中の岩の柱 | 0.44 / 0.45 | 0.46 / 0.45（柱は水面の高さの既存の切り替え） |
| 地下から上へ掘って脱出（20 通り） | 最大 0.19 | 最大 0.19（1 通りだけ 0.15 → 0.19。ほかは同じか小さい） |

- カニの動き（終わりの位置・状態）はすべての場面で変更前と同じ。
- 倒木の画面（`sheet-logcam.jpg`）：
  - 変更前は、1 枚目で倒木の面だけが映ってカニが見えず、2 枚目で急にカニの目の前へ寄る。
  - 変更後は、3 枚とも抜いた円の中にカニが見える。3 枚目は倒木の中を通っている途中で、周りが暗い。
- カメラが固体の中にいるフレーム：歩いて越える 39 → 38、跳んで越える 16 → 25（いちばん長く続いて 8 フレーム = 0.13 秒。
  その間も倒木は抜いて描くので、カニは見える）。
- 地下カメラ：脱出の検査 20 / 20、`dig_test` のカメラが固体の中 0。
- ガラス越しのカメラ：4 辺 + 2 角でカメラは常にガラスの外（外面から 2.6）。

## 6. 残っている問題（重要度・発生条件）

1. **中**：ガラス際の穴の輪郭が、ガラスの面で最大 0.2 広がる（漏斗のような面取り）。
   - 発生条件：トンネルがガラスに届いた所、または 0.1 以内で止まった所。
   - 外から見ると、穴の縁が奥より少し大きく見える。
2. **低**：倒木を越えるとき、カメラが倒木の中を通る間（最大 0.13 秒）は周りが暗い。カニは抜いた円の中に見える。
   - 発生条件：倒木の向こうへ降りる・跳んで越える。
3. **低**：外からの断面検査で、奥のガラスに透け 2 本（変更前から）。
   - 発生条件：水中の奥のガラス際を掘り、地表のすぐ下を見たとき。
4. **低**：ガラス際の帯（内面から 0.1）だけ、距離関数の値が距離の下限より大きくなりうる（傾き 2）。
   - そのため球の追跡は帯の中で最大 0.1 ほど行き過ぎうるが、帯はガラスの当たり判定に接していて、カニ・カメラは入れない。
5. **低**：ふつうの掘削中は、CPU 4 倍遅くで FPS 34（変更前 25）。区画 1 つ（16 ms）が 1 フレームの上限（6 ms）を超えるため。
   - 残りは主に `primDist`・`carve` と、頂点の陰（`solid`）。
6. **低**：引いた視点（zoom 4.5）で倒木を越えると 0.52。置いた直後に遮られて寄る既存の動き（係数 9）。
7. 実機（iPhone / Android）では確認していない。

前回の報告の「残っている問題」のうち、1（ガラスの 1 マス手前の抜け）・2（ガラス際の負荷）・5（倒木のカメラ 0.88）は
この変更で直した。3・4・6・7・8（逆さに近い姿勢・回り込みの脚・メニスカスの線・地表まで掘れない 3 地点・実機）は残っている。

## 7. 見つけた食い違い（文書・コメントとコード）

1. 前回の報告の 7-1 は「直すならガラス際は格子 2 マスより薄い板を開ける（試した 0.22 では減らなかった）」。
   実際の原因は板の厚みの基準ではなく、1 列目の格子点の符号と当たり判定の砂の位置がずれることだった。
2. 前回の報告の 7-2 は「断面の下の部分を残して穴の高さの帯だけ作り直すと減らせる」。測ると、下の部分は既に安く
   （`deepY`）、時間のほとんどは空洞の距離関数（`clip`・`carve`）だった。
3. `AquaCamera.orbitPose` のコメントは「床・天井が離れるときはゆっくり追う」だが、番兵（−2 / 2）へ向けて戻していた。
   そのため離れ始めは速く（1 フレーム 0.16 rad）、コメントのとおりではなかった（直した）。
